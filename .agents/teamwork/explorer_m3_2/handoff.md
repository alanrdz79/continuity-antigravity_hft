## 2. Logic Chain
1. **Elimination of PSA Peering Race Conditions**:
   - *Observation*: Memorystore creation over Private Service Access fails with HTTP 400 if the Google Service Networking VPC peering is not active.
   - *Deduction*: By declaring `depends_on = [var.private_service_access_connection]` on `google_redis_instance.hft_redis` and passing `module.networking.private_service_access_connection` from root, Terraform guarantees that peering is fully established prior to Redis creation.
2. **Selection of STANDARD_HA Tier and Tokyo Co-Location**:
   - *Observation*: Trading engine C3/C4 VM is provisioned in `asia-northeast1-b` (`primary_zone`).
   - *Deduction*: Configuring Redis `location_id = var.primary_zone` (`asia-northeast1-b`) ensures ultra-low round-trip network latency (<100µs) between the trading VM and the primary Redis node. Configuring `alternative_location_id = var.secondary_zone` (`asia-northeast1-c`) provides automatic multi-zone failover (<30 seconds) with zero data loss.
3. **Secret Manager Integration Strategy**:
   - *Observation*: Memorystore generates a random `auth_string` upon creation.
   - *Deduction*: A `google_secret_manager_secret_version` resource linked to `var.redis_auth_secret_id` (from `module.secrets.redis_auth_token_secret_id`) injects the live GCP-generated AUTH token into Secret Manager. The trading engine and emergency shutdown function can query `/versions/latest` without requiring manual secret maintenance.
4. **Memory Policy for Kill-Switch Safety**:
   - *Observation*: In high-throughput HFT, orderbook cache keys could fill the 1 GiB memory limit.
   - *Deduction*: Setting `maxmemory-policy = "volatile-lru"` ensures only keys with TTL are evicted. Because the kill-switch key `hft:emergency:kill_switch_active` has no TTL, it is guaranteed never to be evicted under memory pressure. `activedefrag = "yes"` prevents memory compaction latency spikes.
5. **Sub-Microsecond O(1) Kill-Switch Check**:
   - *Observation*: Network calls to Redis take ~100µs; checking Redis across the network on every trading tick would hurt HFT performance.
   - *Deduction*: The trading engine uses an in-process atomic boolean flag (`std::atomic<bool>` / local cache) synchronized with Redis via Pub/Sub or high-frequency polling. Hot-loop order validation inspects this local atomic flag in ~15 to 30 nanoseconds ($O(1)$ constant time), while Redis acts as the authoritative distributed source of truth.

## 1. Architectural Overview & Context

In a real-time High-Frequency Trading (HFT) infrastructure on Google Cloud Platform, market data ingestion and state persistence operate across two complementary storage tiers:

1. **Ultra-Low-Latency In-Memory State Tier (Cloud Memorystore Redis)**:
   - Retains current state, top-of-book depth, active orders, and the critical atomic circuit breaker kill-switch flag (`hft:emergency:kill_switch_active`).
   - Latency target: Sub-millisecond (< 500 µs via Private Service Access).

2. **High-Throughput Persistent Time-Series Tick Storage Tier (Cloud Bigtable SSD)**:
   - Ingests and stores every raw trade execution, Level-2 (L2) orderbook depth update, and microsecond-level latency/risk metric generated by the trading engine and Binance WebSocket feeds.
   - Serves as the authoritative source of truth for post-trade transaction cost analysis (TCA), slippage calculation, orderbook replay, and machine learning feature pipelines.
   - Latency target: Deterministic single-digit millisecond reads/writes over gRPC with high concurrency and sustained write throughput exceeding 100,000 mutations per second per cluster node.

## 2. Cloud Bigtable Instance & Cluster Specification

### 2.1 Hardware Media: Strict SSD Enforcement
- **Storage Type**: **`SSD`** (Solid State Drive) is **strictly mandated**.
- **Rationale**: HDD storage in Bigtable relies on spinning magnetic platters. While HDD is cheaper for batch archival, its sequential seek times (10-15 ms) and severe IOPS bottlenecks (100-500 IOPS per node vs. 10,000-14,000 IOPS for SSD) introduce catastrophic tail latency spikes (p99 > 100 ms) that violate HFT operational thresholds. SSD delivers consistent, predictable read/write latency (< 5 ms at p99).

### 2.2 Zonal Placement & Network Locality
- **Cluster ID**: `hft-tick-cluster-01`
- **Cluster Zone**: `asia-northeast1-c` (configured via `secondary_zone` variable).
- **Rationale**: While the C3/C4 Compute Engine trading instances run in `asia-northeast1-b` (closest to specific network peering points), provisioning the Bigtable cluster in `asia-northeast1-c` achieves cross-zonal failure isolation while maintaining sub-millisecond intra-region fiber network round-trip times (RTT) across Google's Jupiter network fabric.

### 2.3 Sizing & Node Capacity
- **Instance Name**: `hft-tick-store` (configurable via `var.bigtable_instance_name`).
- **Cluster Node Count**: Static `num_nodes = 1` for demo/development baseline; scales linearly with workload.
- **Autoscaling Capability**: The proposed module introduces an optional dynamic `autoscaling_config` block (`min_nodes = 1`, `max_nodes = 5`, `cpu_target = 70`), controlled via `enable_bigtable_autoscaling = false` by default to prevent unexpected cost runaway while providing production elasticity.
- **Deletion Protection**: Set to `deletion_protection = false` to enable teardown and testing flexibility during development/demo phases, while supporting parameterized enablement in production.

## 4. Garbage Collection (GC) Retention Strategy

In high-frequency market data pipelines, tick updates occur at rates of thousands of events per second per trading pair. Without rigorous garbage collection policies, SSTables swell uncontrollably, leading to:
1. Massive storage cost inflation.
2. Degraded read latency caused by scanning through numerous obsolete cell versions and tombstone markers during compaction cycles.

### 4.1 Tiered Retention Policies

| Column Family | Policy Type | Retention Horizon | Rationale |
|:---:|:---:|:---:|---|
| `'t'` (Trades) | `max_age` | **30 days (`720h`)** | Trades are critical for monthly P&L reconciliation, audit compliance, and trade-cost analysis (TCA). Lower event frequency allows longer retention. |
| `'q'` (Quotes) | `max_age` | **7 days (`168h`)** | Orderbook quotes constitute > 90% of total write volume. A 7-day rolling window provides sufficient depth for intraday and weekly signal calibration while bounding storage growth. |
| `'m'` (Metrics) | `max_age` | **14 days (`336h`)** | Provides a two-week window for latency anomaly analysis, network drift detection, and SLA verification against Binance matching engines. |

### 4.2 Lifecycle Safety (`deletion_policy = "ABANDON"`)
- In Terraform, modifying or destroying Bigtable tables with active GC policies on replicated instances can cause API lockup if Bigtable attempts to synchronously purge underlying data before schema destruction.
- Declaring `deletion_policy = "ABANDON"` on all `google_bigtable_gc_policy` resources ensures that Terraform can safely destroy or update the configuration without recreation deadlocks.

## 5. Row Key Architecture & Mathematical Proof

### 5.1 Exact Row Key Formula
```
{symbol}#{Long.MAX_VALUE - timestamp_micros:019d}#{seq_id:010d}
```

### 5.2 Mathematical Proof of Chronological Inversion

1. **Lexicographical Sort Invariant**:
   - Cloud Bigtable stores all rows in strict lexicographical (byte-by-byte alphabetical) order.
   - If two keys $K_A$ and $K_B$ share the same prefix (e.g., `BTCUSDT#`), the comparison evaluates the numerical string following the delimiter `#`.

2. **Mathematical Inversion**:
   - Let $T_1$ and $T_2$ be Unix timestamps in microseconds, where $T_1 < T_2$ ($T_2$ is strictly newer than $T_1$).
   - Let $L_{\max} = \text{Long.MAX\_VALUE} = 2^{63} - 1 = 9,223,372,036,854,775,807$.
   - The inverted timestamps are:
     $$T_{inv,1} = L_{\max} - T_1$$
     $$T_{inv,2} = L_{\max} - T_2$$
   - Since $T_1 < T_2$, subtracting a larger number yields a strictly smaller result:
     $$T_{inv,2} < T_{inv,1}$$

3. **Fixed-Width Zero-Padding Invariant**:
   - Lexicographical string comparison matches numerical ordering **if and only if** the strings have identical fixed lengths.
   - In standard ASCII, `"9" > "10"`, but `"09" < "10"`.
   - $L_{\max}$ contains exactly 19 decimal digits.
   - By formatting $T_{inv}$ with `:019d`, every inverted timestamp is guaranteed to occupy exactly 19 characters with leading zeros:
     $$\text{str}(T_{inv,2}) <_{\text{lex}} \text{str}(T_{inv,1})$$
   - Consequently, **newer ticks sort before older ticks**.

4. **Tie-Breaking with Sequence ID**:
   - Within a single microsecond, multiple market events may occur (e.g. batched trade executions).
   - The suffix `#{seq_id:010d}` provides deterministic tie-breaking. A 10-digit zero-padded integer accommodates up to 9,999,999,999 sequential events per microsecond.

### 5.3 O(1) Head-of-Log Range Scans
- **Trading Engine Requirement**: The trading engine or risk monitor needs to inspect the latest tick for symbol `BTCUSDT`.
- **Query Execution**:
  - `start_row_key = "BTCUSDT#"`
  - `end_row_key = "BTCUSDT#9223372036854775807#9999999999"`
  - `limit = 1` (or `limit = N` for the last N ticks).
- **Index Traversal**: Bigtable's SSTable B-tree index locates the first entry starting with `BTCUSDT#` in $O(1)$ tablet index seek time.
- **Result**: The very first row returned by the iterator is the absolute newest tick in the system. No full-table scans, no reverse iteration overhead, and zero historical record traversal.

### 5.4 Hotspotting Mitigation & Pre-Splits
- While pure timestamp row keys can concentrate writes onto a single tablet server (hotspotting), prefixing with `{symbol}#` partitions the keyspace across multiple asset symbols (`BTCUSDT#`, `ETHUSDT#`, `SOLUSDT#`).
- The module provisions `split_keys = ["BTCUSDT#", "ETHUSDT#", "SOLUSDT#"]` upon table creation, instructing Bigtable to pre-distribute tablets across available cluster nodes from second zero.

## 6. IAM Least-Privilege Access Control

The Cloud Bigtable storage module enforces Google Cloud least-privilege security by using non-authoritative instance-level IAM bindings:

```terraform
resource "google_bigtable_instance_iam_member" "hft_engine_user" {
  count    = var.hft_engine_sa_email != "" ? 1 : 0
  instance = google_bigtable_instance.tick_store.name
  project  = var.project_id
  role     = "roles/bigtable.user"
  member   = "serviceAccount:${var.hft_engine_sa_email}"
}

resource "google_bigtable_instance_iam_member" "dataflow_worker_user" {
  count    = var.dataflow_worker_sa_email != "" ? 1 : 0
  instance = google_bigtable_instance.tick_store.name
  project  = var.project_id
  role     = "roles/bigtable.user"
  member   = "serviceAccount:${var.dataflow_worker_sa_email}"
}
```

### Security Properties
1. **Scope Restriction**: `roles/bigtable.user` grants read and write permissions to table data (`bigtable.tables.readRows`, `bigtable.tables.mutateRows`) without granting permissions to drop instances, alter clusters, or modify IAM policies.
2. **Defense-in-Depth**: Even though project-level bindings exist in `modules/iam`, explicit instance-level bindings guarantee that only designated trading engine and Dataflow identities can access the `hft-tick-store` instance.
3. **Non-Authoritative Safety**: `google_bigtable_instance_iam_member` modifies only the specified member-role tuple, preventing accidental eviction of existing administrative credentials.
